# 约束理论 (Theory of Constraints, TOC)

> **证据层级：B（实践框架）。** TOC 与五聚焦步骤可追溯到 Goldratt 原作和专业机构资料，主要由管理实践与案例支持；应用时不得把单一约束或固定步骤写成对所有复杂系统都成立的普遍因果规律。

## 概述

约束理论把组织或流程视为一个为目标服务的整体系统：在某一时期，系统产出受到少数约束限制；改善应围绕当前约束展开，而不是让每个局部都各自追求最高效率。

一句话版本：**系统的改善速度取决于当前约束；先让整体流动得更好，再谈局部更忙。**

## 核心结构：五聚焦步骤

正式进入五步前，先明确系统边界、目标及衡量目标的指标；目标含糊时，“约束”也无法可靠识别。

1. **识别约束（Identify）** — 找出当前最限制系统实现目标的资源、环节、市场条件或政策规则。
2. **充分利用约束（Exploit）** — 在不做重大新增投入的前提下，减少约束处的等待、返工、切换和低价值占用，让其时间用于真正贡献目标的工作。
3. **其他环节服从约束（Subordinate）** — 调整非约束环节的节奏、优先级和在制品，使它们保护并服务约束，而不是制造堆积或让约束断料。
4. **提升约束（Elevate）** — 当前三步仍不足时，通过增加能力、改变规则、重构流程、自动化或外部资源提高约束容量。
5. **约束打破后回到第一步（Repeat）** — 改善后约束通常会迁移；重新识别，并警惕旧规则和惯性成为新约束。

### 局部优化边界

非约束环节多生产一件，并不自动增加系统有效产出，反而可能增加在制品、等待、切换和返工。TOC 因而区分“资源很忙”与“系统目标改善”：

```text
局部产出增加 ≠ 系统有效产出增加
非约束超前生产 → 在制品堆积 → 交付时间与风险上升
```

“服从约束”也不等于让其他资源闲置而不思考。非约束应保留必要的保护能力，承担质量前移、维护、改进或能减少约束负担的工作；判断标准始终是对整体目标和流动的贡献。

## 可执行步骤

1. **定义系统与目标** — 写清客户价值、有效产出、交付时间、在制品/投入和必要保护条件，避免只用单一利用率评价。
2. **画出端到端流动** — 从需求进入到价值交付，记录队列、等待、返工、阻塞和各环节实际完成率。
3. **用证据识别约束** — 观察持续排队、下游饥饿、约束时间损失和需求/能力关系；不要仅凭“看起来最忙”判断。
4. **先充分利用** — 清除约束处不必要的会议、切换、返工和低优先级工作，确保输入质量与准备就绪。
5. **让其他环节服从** — 限制上游在制品，按约束节奏释放工作，设置适量缓冲，并把质量检查尽量前移。
6. **再决定提升投入** — 若约束仍限制目标，评估增员、培训、外包、工具、自动化或规则调整；先验证投入确实改善整体。
7. **观察迁移并复盘** — 比较有效产出、交付时间、在制品和质量；约束迁移后重新开始，不继续优化旧约束。

## 工作示例

场景：软件团队开发很快，但版本总在代码审查阶段排队。

- **目标**：稳定、可恢复地交付通过验收的变更，而不是最大化开发提交数。
- **识别**：数据表明多数交付时间消耗在审查队列，审查者频繁被紧急事务打断；测试并非持续排队点。
- **充分利用**：统一小批量提交标准，提前跑静态检查，减少缺少上下文造成的往返；为审查者划定无打断时段。
- **服从**：限制同时进入审查的变更数量；开发人员优先修正审查反馈、完善测试和准备下一项，不继续堆积大批待审代码。
- **提升**：在前述措施仍不足时，培养第二位审查者，或自动化可确定的检查；高风险语义审查仍保留人工责任。
- **再识别**：审查队列下降后，约束可能迁移到验收环境。此时停止围绕旧约束追加资源，回到第一步。

这个例子也说明局部优化的边界：开发提交数上升但已验收交付不变，不是整体改善；自动化让审查更快但引入漏检，也不能只按速度判定成功。

## 注意事项与适用边界

- **先定义目标，再找约束**：不同目标会得到不同约束；不能把“最贵”“最忙”或“抱怨最多”的环节直接等同于约束。
- **约束不一定是设备或人**：也可能是政策、批量规则、市场需求、技能、审批或管理注意力；需要证据区分。
- **不要把约束逼到无缓冲的满载**：波动存在时，极限利用率可能放大排队和中断；应保护约束并保留恢复能力。
- **局部效率指标可能与整体冲突**：上游利用率、单件成本或部门产量提高，可能以更多库存和更长交付时间为代价。
- **提升之前先充分利用和服从，但不能教条拖延必要投资**：若安全、合规或明确容量缺口要求立即行动，应按风险处理。
- **TOC 不是一次性找瓶颈**：改善会使约束迁移；旧流程、KPI 和惯性可能变成新的政策约束。

## 与现有模型的差异

| 模型 | 主要关注 | 与 TOC 的差异 |
|------|----------|---------------|
| **木桶原理** | 最短板限制整体表现 | 木桶原理是静态比喻；TOC 提供围绕当前约束改善、服从、提升和重新识别的循环 |
| **系统思维** | 关系、反馈、延迟和整体行为 | 系统思维范围更广；TOC 给出以系统目标和约束为中心的干预顺序 |
| **PDCA 循环** | 计划、执行、检查、行动的通用改进循环 | PDCA 管理迭代过程；TOC 决定改进焦点应放在哪里，二者可配合 |
| **反馈回路** | 行为如何被增强或平衡 | 反馈回路解释动态因果；TOC 聚焦限制目标实现的当前杠杆点 |
| **帕累托法则** | 少数因素贡献多数结果 | 帕累托用于筛选重要因素；TOC 强调系统流中具有限制作用的约束，不等同于问题数量最多的类别 |

## 适用场景

- 生产、供应链和库存流动改善
- 软件研发、内容生产、审批和服务交付流程
- 项目组合中共享专家、设备或环境的容量管理
- 交付周期长、在制品多、局部很忙但整体产出不升的系统
- KPI 促使部门各自优化，整体却出现堆积、返工或延误的组织
